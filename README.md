# CodeSides

Собирает из одного исходника мода **два jar**, серверный и клиентский, физически вырезая из каждого код
чужой стороны. Не «не вызывать на клиенте», а именно вырезать: в клиентском jar серверных классов, методов и
полей нет вовсе, декомпилировать нечего. Плюс верификатор, который не даёт общему коду сослаться на
вырезанное и получить падение уже у игрока.

Зачем: серверная логика (античит, экономика, доступы, приватные данные) не уезжает в раздачу клиента.

Gradle-плагин, ядро на ASM и аннотации лежат в одном артефакте: `com.mrleonardos:codesides:1.0.0`.

## Подключение

Пока библиотека не опубликована в публичный репозиторий, публикуем локально:

```bash
cd CodeSides
./gradlew publishToMavenLocal      # нужен JDK 21
```

`settings.gradle` мода:

```groovy
pluginManagement {
	repositories {
		mavenLocal()
		gradlePluginPortal()
	}
}
```

`build.gradle` мода:

```groovy
plugins {
	id 'com.mrleonardos.codesides' version '1.0.0'
}

repositories {
	mavenLocal()
	mavenCentral()
}

dependencies {
	compileOnly 'com.mrleonardos:codesides:1.0.0'
}

codeSides {
	archiveBaseName = 'mymod'
	serverOnlyResources = ['assets/mymod/secret/**']
}
```

Аннотации подключаются `compileOnly`: в рантайм они не идут, из выходных классов стираются, зависимости на
CodeSides у готового мода нет.

## Minecraft 1.7.10 и GTNH

Резать надо **уже реобфусцированный** jar, иначе имена классов Minecraft в сторонах разъедутся с маппингами.
С RetroFuturaGradle / GTNHGradle это одна строка:

```groovy
codeSides {
	inputJar = tasks.named('reobfJar').flatMap { it.archiveFile }
}
```

Плагин сам подхватит зависимость задач: `gradlew build` соберёт `reobfJar`, а из него сделает
`mymod-<версия>-server.jar` и `mymod-<версия>-client.jar` в `build/libs`.

Без `inputJar` режутся каталоги сборки (`build/classes` + `build/resources`), такой вариант годится для
модов без реобфускации и для проверок в CI.

## Как размечать код

```java
@ServerSide                                  // весь класс — только в серверном jar
public final class EconomyService { … }

public class Machine {
	@ClientSide void render() { … }          // метод вырежется из серверного jar
	@ServerSide  void save()   { … }         // и наоборот
	@ServerSide  int  balance;               // поля тоже
}
```

Пакет целиком размечается через `package-info.java`, метка каскадит на все подпакеты:

```java
@ServerSide
package com.example.mymod.server;
import com.mrleonardos.codesides.ServerSide;
```

Ставить можно на класс, метод, конструктор, поле и пакет. **Непомеченное считается общим** и попадает в оба
jar: метить нужно только то, что обязано жить на одной стороне. Более глубокая пометка побеждает более
широкую: класс в серверном пакете можно вернуть в общие, пометив его `@ClientSide`.

Уже размеченный FML-код тоже режется: `@SideOnly(Side.CLIENT)` понимается наравне с `@ClientSide`.

### Что пометить нельзя

Две вещи компилятор решает за нас ещё до CodeSides, поэтому пометка на них не работает. Верификатор их
находит и роняет сборку, вместо того чтобы делать вид, что вырезал:

**Константы времени компиляции.** Значение `static final` поля примитивного типа или String javac
подставляет прямо в место чтения, ссылки на поле в байткоде не остаётся. Удаление поля не убирает значение
из чужого jar:

```java
@ServerSide public static final String DB_PASSWORD = "…";    // пометка ничего не даст
@ServerSide public static String dbPassword() { … }          // значение уедет вместе с методом
```

Так же работает пометка всего класса: `@ServerSide` класс с `public static final String` вырежется, а его
строки останутся в клиентском jar внутри тех классов, которые их читали. Верификатор даёт нарушение
`constant` на саму пометку и `inlined` на класс, где найдено значение вырезанной константы.

**Поле с инициализатором.** `@ServerSide Supplier<String> f = () -> "…"` уберёт поле, но присваивание
останется в `<init>`, а вместе с ним и тело лямбды или анонимки. Нарушение `initializer` говорит именно
об этом. Инициализируй такое поле в помеченном методе или держи состояние целиком в помеченном классе.

### Что уходит следом автоматически

Компилятор превращает лямбды в скрытые методы `lambda$...`, анонимные классы в `Outer$1`, доступ к
приватным членам в методы доступа `access$...`. Аннотаций на них нет, поэтому CodeSides считает достижимость:
сгенерированный член, до которого не дотягивается ни одна ссылка из оставшегося кода, удаляется вместе с
породившим его методом. Без этого тело серверной лямбды уехало бы в клиентский jar целиком.

Мосты generic-override (`ACC_BRIDGE`), служебные поля enum и `$deserializeLambda$` при этом остаются: их
зовёт JVM, а не код, поэтому входящих ссылок у них нет и по достижимости они выглядели бы мусором.

## Ресурсы

Ресурсы раскладываются масками. Это glob по пути внутри jar, где `*` не переходит через `/`, а `**` переходит:

```groovy
codeSides {
	serverOnlyResources = ['assets/mymod/secret/**', 'data/mymod/economy.json']
	clientOnlyResources = ['assets/mymod/gui/*.json']
}
```

По умолчанию из серверного jar убираются клиентские медиа: `textures`, `models`, `sounds`, `shaders`,
`particles`, `font`, `blockstates`, `sounds.json` и файлы `*.png`, `*.ogg`, `*.wav`, `*.mcmeta`, `*.obj`,
`*.mtl`, `*.vsh`, `*.fsh`, `*.glsl` внутри `assets/`. Языковые файлы остаются общими намеренно: сервер тоже
переводит строки. Отключается через `defaultResourceRules = false`.

Файл, попавший разом под серверную и клиентскую маску, роняет сборку: молча выбирать сторону за автора
нельзя.

## Главное правило

**Общий код не должен ссылаться на символ одной стороны.** Иначе в чужом jar осталась бы ссылка на
вырезанное, и мод упал бы `NoClassDefFoundError` / `NoSuchMethodError` / `AbstractMethodError` уже у игрока,
в рантайме, а не на сборке.

Верификатор ловит это и при `strict = true` (по умолчанию) роняет сборку с точным указанием места. Проверяются:

- ссылки на вырезанные классы, методы и поля, включая тела лямбд, `invokedynamic`, типы в `try/catch`,
  generic-сигнатуры и аннотации (значения-массивы, вложенные аннотации, аннотации параметров и значения по
  умолчанию тоже);
- абстрактные контракты: вырезанная реализация абстрактного метода оставляет класс без контракта. Контракты
  типов платформы (`Comparable`, `Supplier`, `Runnable`, `Iterable`) проверяются всегда, для этого ничего
  подключать не нужно. Контракты Minecraft, Forge и библиотек (`IInventory` и прочее) читаются по compile
  classpath и отключаются через `verifyAgainstClasspath = false`;
- константы времени компиляции: помеченная константа (`constant`) и значение вырезанной константы,
  найденное в байткоде этой стороны (`inlined`);
- присваивание вырезанного поля в `<init>` или `<clinit>` (`initializer`).

Правильный приём: серверную логику прятать за общим интерфейсом, а реализацию помечать `@ServerSide`.

```java
public interface Balance { int balanceOf(String player); }   // общий

@ServerSide
public final class Economy implements Balance { … }          // только сервер
```

`strict = false` превращает нарушения в предупреждения. Это режим миграции существующего мода, а не рабочий:
пока нарушения есть, раздельные jar'ы могут падать в рантайме, а найденные утечки констант остаются
в клиентском jar.

## Задача и настройки

`splitSides` режет мод и пишет обе стороны в `build/libs`. Подвешена на `assemble`, так что хватает
обычного `build`.

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `archiveBaseName` | имя проекта | база имени: `<base>-<версия>-server.jar` |
| `archiveVersion` | версия проекта | версия в имени архивов |
| `inputJar` | не задан | резать готовый jar вместо каталогов сборки |
| `strict` | `true` | ронять сборку при нарушении контракта |
| `server` / `client` | `true` | какие стороны собирать |
| `universalJar` | `true` | оставлять обычный `jar` со всем кодом |
| `verifyAgainstClasspath` | `true` | читать contract-типы Minecraft, Forge и библиотек по compile classpath |
| `defaultResourceRules` | `true` | добавлять маски ресурсов по умолчанию |
| `serverOnlyResources` / `clientOnlyResources` | `[]` | маски ресурсов одной стороны |

Обычный `jar` остаётся для dev-запусков, но **раздавать нужно `-server` и `-client`**: в универсальном jar
серверный код присутствует физически. Когда dev-запуск не нужен, ставьте `universalJar = false`.

Обе стороны режутся и проверяются до записи, и оба архива пишутся, только когда обе стороны чистые. Прошлые
архивы задача удаляет в начале, так что после красной сборки в `build/libs` не останется половины пары:
CI-шаг «выложить `build/libs/*.jar`» не раздаст серверный jar от нового кода вместе с клиентским от старого.

Архивы пишутся детерминированно (отсортированные записи, фиксированное время), так что сборка воспроизводима.

## Ограничения

- Ссылки в оставшемся коде не переписываются: нарушение контракта это ошибка сборки, а не то, что CodeSides
  чинит сам.
- Доступ к вырезанному через рефлексию по строковому имени верификатор не увидит.
- Контракты Minecraft, Forge и библиотек проверяются только при доступном compile classpath. Типы платформы
  (`java.*`, `javax.*`) читаются из JVM сборки и доступны всегда.
- Инлайненное значение из чужого jar не вычищается: CodeSides его находит и роняет сборку, переписать чужой
  байткод он не берётся.
- Поиск инлайненного значения идёт по константному пулу. Склейка (`"url=" + SECRET`) даёт компилятору новую
  константу, а маленькие числа лежат прямо в инструкции, а не в пуле, поэтому такие случаи не находятся.
  Вывод один: не метить константы, метить методы.

## Сборка самой библиотеки

```bash
./gradlew build                 # компиляция + 32 теста
./gradlew publishToMavenLocal   # публикация com.mrleonardos:codesides:1.0.0
```

JDK 21 для сборки инструмента, байткод Java 8: тот же jar годится и как gradle-плагин, и как
`compileOnly`-зависимость мода на Java 8. Единственная зависимость: ASM.
